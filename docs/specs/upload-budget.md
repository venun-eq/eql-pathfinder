# Upload byte budgets, feedback daily caps, and Worker edge hardening

**Why:** Independent review of the pre-GitHub hardening found four remaining abuse and reliability gaps once `server/` is public: a single registered install can still upload ~1.2 GB/day into D1 (1 MiB `facts` × 200 requests × 6 MiB), plain text feedback and roadmap votes have no daily cap beyond 10/min, a transient R2 failure during `PUT /v1/feedback/:id/shot` permanently burns the report's one-time screenshot token, and `api.eqlpathfinder.workers.dev` remains enabled in production where it bypasses the zone's `api.eqlpathfinder.com` edge WAF rate limit.
**Players:** everyone. Legitimate players see no change (all caps sit 5–20× above the heaviest real production day, and active copies are all on 0.10.3+); one runaway or abusive caller can no longer fill D1, exhaust daily write quotas, or lose a report screenshot on a transient storage hiccup.

## What the player sees
`site/privacy.html`'s "Your internet address" section notes that the same 2-day hashed connection code used for sharing and report screenshots also caps how many feedback reports and roadmap votes one connection can send in a day.

## Edge cases
- **First upload of the day vs batch size:** per-install byte check requires `usedBytes > 0` before refusing `usedBytes + changedBytes > MAX_BYTES_PER_DAY` (still bounded by `MAX_BODY = 6 MiB`), so a legitimate batch can never permanently wedge an install across days.
- **Unchanged re-sends at unit or byte limits:** when `changed.length === 0`, `changedBytes` is 0 and neither the per-install byte budget nor the global unit/byte fuses block the request (still bounded by `MAX_REQUESTS_PER_DAY = 200`).
- **Taking a roadmap vote back (`on: false`) at the daily vote cap:** `DELETE FROM votes` bypasses `voteLimit` so players can always withdraw a vote as promised on the privacy page.
- **Malformed feedback or vote requests (`400`):** payload fields and roadmap item existence are validated before checking or incrementing `feedback_ips`, so bad input never consumes daily quota.
- **Rolling D1 migration before Worker deploy:** `ALTER TABLE usage ADD COLUMN bytes INTEGER NOT NULL DEFAULT 0` and a separate `feedback_ips` table leave existing `usage` and `shot_ips` queries working unchanged while the previous Worker version is still serving.
- **Older installed copies (`workers.dev` removal):** production D1 queries on 2026-11-23 confirmed all active installs (`installs` 30d and `app_usage` 14d) are on `0.10.3`–`0.10.28` (`DefaultApi` switched to `api.eqlpathfinder.com` in `0.9.32`); setting `min_app = 0.10.0` alongside disabling production `workersDev` strands no active copies.

## Decisions
- **Limits sized from live production data (2026-11-23):** largest `units.facts` blob in production is 8,974 B (avg 914 B), heaviest install-day is 1.26 MB / 1,431 units, and heaviest whole day across all installs was 4,537 units (from `usage`; `units.received` undercounts re-sends, which showed ~2,900). Setting `MAX_FACTS = 128 KiB` (~96 KiB compressed), `MAX_BYTES_PER_DAY = 16 MiB`/install, `max_upload_bytes_per_day = 200 MiB`, and `max_units_per_day = 200,000` protects D1 storage and the writes Workers Paid includes (raised on 11-24 from 50 MiB and 15,000, which were sized on nine copies and would have stopped a public launch at about ten new sharers a day). The headroom over real play is not 5-20x everywhere: one install sent 2,977 units against its 3,000 cap, the global units cap is about 44x the busiest day before the launch (raise it when real daily units pass half of it), and `MAX_REQUESTS_PER_DAY = 200` is 2.6x the busiest real day (77), so it counts only uploads that changed nothing (`changed.length === 0`); the byte and unit caps bound changed uploads.
- **Migration `0009_upload_budget.sql`:** adds `bytes INTEGER NOT NULL DEFAULT 0` and `usage_day` index on `usage`, plus idempotent `feedback_ips (code, day, feedback, votes)` keyed by the existing 2-day HMAC `connectionCode` and pruned after 2 days by `scheduled()`. Keeping `shot_ips` separate preserves zero-downtime compatibility during migration and rollback.
- **Restore `shot_token` on R2 failure:** `attachShot` still claims `shot_token = NULL` atomically before `SHOTS.put` to prevent concurrent double-writes, and restores `shot_token` (`WHERE id = ? AND shot_token IS NULL AND shot IS NULL`) in `catch` before rethrowing so transient R2 errors remain retryable.
- **Production `workersDev: false` + `staging:sleep`:** closes the `api.eqlpathfinder.workers.dev` bypass around the zone's `api.eqlpathfinder.com` WAF rate limit, and adds `mode === "staging-sleep"` (`npm run staging:sleep`, still bound to `EQLP_D1_STAGING`) so staging's `workers.dev` route is cleanly disabled after smoke tests. Release note sets `job: true` so `ship.ps1` updates the NAS CLI build.
- **Taking it back:** `max_upload_bytes_per_day`, `max_units_per_day`, `max_feedback_per_ip`, `max_feedback_per_day`, and `max_votes_per_ip` can each be raised or disabled (`"0"`) live in D1 `config` without a deploy; reverting the Worker deploy leaves `usage.bytes` (default 0) and `feedback_ips` harmless.

## Not doing
- Changing `Feedback.cs` error copy in the desktop app (existing copies already display a calm retry message on HTTP 429 and preserve the player's text).
- Custom domain for `api-staging` (`npm run staging:sleep` keeps staging unreachable when idle without extra DNS/WAF surface).
