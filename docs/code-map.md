# Code map: where things are

Open the right forty lines, not the whole file. Grep the names below: there are no line numbers, because they rot.
`tools/mapcheck.mjs` (a step of `tools/check.ps1`) fails when a file or a name on this page is gone, so a rename comes
with its line here. How things work is on the other pages (docs/README.md). How to render or query is in
`.claude/skills/`.

Short forms: App = `src/EqlPathfinder.App`, Engine = `src/EqlPathfinder.Engine`, web = `src/EqlPathfinder.App/web`.

Every number a player sees, how it is worked out and the test that holds it: [calculations.md](calculations.md).

## 1. How data moves

**Log line to page**, one hop per step:
1. Log file → `LogReader.ReadFrom` (whole lines only; returns the next offset), called by `PathfinderEngine.ReadFile`. First read: `TrackerService.ImportHistoryAsync` → `ImportCoreAsync`. Then `TrackerService.Step` tails `Logs.LivePath` from `Checkpoint.Offsets` (the loop in `Start` wakes every 0.5 s while the game runs, 5 s otherwise).
2. `PathfinderEngine.ProcessLine` → `LogLine.TryParse` (time + body) → `Tracker.OnLine` → `LineParser.Parse` → one `LogEvent` record (`Parsing/LogEvents.cs`) or null.
3. `Tracker.Apply(LogEvent)` (a `switch` on the event type) → changes `EngineState` → emits through `ITrackerSink`: `OnVisitClosed`, `OnVisitUpdated`, `OnKill`, `OnLoot`, `OnLevel`, `OnHighTier`.
4. `TrackerService.Sink` → `PathfinderStore.Batch` plus in-memory `_history` / `_fieldKills` → `SaveCheckpoint` → `PathfinderStore.Commit` (tables `visits`, `kills`, `loot`, `levels`; the checkpoint is JSON in `meta` under `checkpoint:<character>`).
5. Overlay: `Step` → `Publish` → `BuildSnapshot` → event `SnapshotReady` → handler in `App.StartTracking` → `OverlayWindow.Update(LiveSnapshot)`. A level, trio or race change there also calls `MainWindow.Refresh`.
6. Page data: `MainWindow.Refresh` (15 s `_timer` while visible, `NavigationCompleted`, and after most page messages) → `App.SettingsForPage` (on the UI thread) → `svc.Query(s => PageData.Build(s, snap, campaign, settings))`, which runs on the tracker thread → `JsonSerializer.Serialize(payload, PageJson.Options)` (camelCase) → `PostWebMessageAsJson`.
7. Page: core.js `window.chrome.webview.addEventListener("message")` → `dispatchHost` → every `onHost` listener. Core's listener takes a message **without `kind`** as `data`, calls `campOnData()`, then `render()` → `renderHome`, `renderCampaign`, `renderRoster`, `renderCrawls`, `renderLoot`, `renderRelevels`, `renderSettings`, then `show(page, true)` (which draws `drawRace` / `drawRelevels` / `drawLootChart` and asks for the open page's answers).

**Page to window and back:**
1. core.js `post(type, extra)` → `chrome.webview.postMessage({ type, ...extra })`.
2. `MainWindow.OnMessage(json)` → `switch (type)` (table in section 3). Cases that `break` (`farmRate`, `routeMetric`, `setting`) end in `Refresh()`: their answer is a new data message.
3. The rest answer with `new { kind = "...", ... }` (Ask: the `AskAnswer` record, whose first field `Kind` is `"ask"`) via `PostWebMessageAsJson`; network answers go through `MainWindow.PostAsync`.
4. core.js's `onHost` routes `loot`, `sharePreview`, `shareStatus`, `ask`, `upgrade`, `usagePreview`; campaign.js, help.js and report.js each add an `onHost` for their kinds. Any other message that has a `kind` is ignored by core and never replaces `data`.

**`--snapshot` preview vs the real window** (`DevSnapshots.Run`, `DevSnapshots.CaptureWeb`): it builds the page data as the window does (`PageData.Build`, with `App.SettingsForPage` on the settings of a new player who took the tour, left as `WelcomeWindow.MarkTourFinished` leaves them, and stand-ins for what only a running app knows: `version` "0.4.0", `updatesEnabled`, `gameRunning`, `logsDir`, `character`), writes `preview.html` = index.html + a closing script with the demos (`window.askDemo = ...`) and `window.previewMessages` (the page data, then Loot's `{ kind: "loot", rows }`), and loads it in an off-screen WebView2 at `https://preview.local/`. There it posts both messages with `PostWebMessageAsJson`, as `Refresh` does, so core.js's own listener takes them; it waits up to five seconds for `data` and `lootRows` and goes on either way, adding its own line to `main-js-errors.txt` when they never arrived. Opened in Chrome, where `chrome.webview` is missing, the engine's stand-in (`WindowStandIn.Script` in `Pages/WindowStandIn.cs`: a real `EventTarget` that keeps a copy of what the page posts in `chrome.webview.posted`) is written before `js/core.js`, and the closing script sends it the same two messages with `dispatchEvent`. The page tests run that same text in headless Edge on every check (`AppPageTests` reads that neither writes a `chrome.webview` of its own). Nothing handles `WebMessageReceived`, so `post()` goes nowhere and no other message arrives: each shot assigns answers to globals (`askAnswer`, `upg`, `campOpts`, `sharePreview`, `shareStatus`, `roadmapItems`) and calls the page's `render…()` and `show()` through `ExecuteScriptAsync`. Script errors go to `<out>/main-js-errors.txt`. Anything that talks to the window: `EQLPATHFINDER_SELFTEST=mock` (`App.SelfTestMockAsync`).

**Where page data is built.** `PageData.Build` (`Pages/PageData.cs`) assembles the data message; `MainWindow.Refresh` and `DevSnapshots.Run` both send what it returns, written with `PageJson.Options`. `PageDataTests` lists every field and holds the message to the one the window sent before it moved (11-17). Ask's Every place sends `cost` per row and `falls` per place (`RouteAnalysis.CostPerLevel`, `Ask.Falls`, one `Fit.Slope` for all). The pages only draw them.

- `reinc` = `TrackerService.ReincarnationData(campaign)`, read by every page: `levelCap` and `newLevels` (the expansion in force: name, day, old cap, cap, the trio's count at the first new level; null before its day: pages say "No route past 50 yet" from it), `classes`/`races` (roster, passives, entered counts), `journeys` (`Journeys()`), `home` (`AskPage(...)`: Home's route or farm answer), `journeyRaces` (`Analysis/JourneyRace.cs`: the relevel race for Relevels `all`, Home `now`, the between card `next` and `own`: rows re-figured to a target XP, band, splits, best of each, `ahead`; pages draw it), `homeNow` (`HomeState.Of`: Home's state, the relevel on now, the parked ones; open relevels come from `Relevels.Of` in Analysis/Relevels.cs: the roster's reincarnations, with a journey when one was played), `paces` (`RelevelPaceData`), `campaign` (`CampaignData` → `Campaign.Evaluate` with `Relevels.Of`: reincarnated runs come first, in the order they happened, "leveling" while their relevel is open and "done" back at the cap, plus `Campaign.Fixes`), `farm`/`farmRate`/`farmSource` (`FarmInfo`, `FarmRateNow`, `RouteAnalysis.FarmSource`; the rate is worked out each time, never stored: readers get it as an argument), `preferences`. Read by no script: `era`, `completionist`, `farmRateManual`.
- `settings` = a `PageSettings` from `App.SettingsForPage` (built on the UI thread, outside the query; every setting the app fills is `required`, and the JSON's order is the order they're declared in): settings.js and most others.
- Not in it (asked for): Ask → `TrackerService.AskPage`; Loot rows → `AllLootCompact`; Upgrades → `UpgradePage.Build` (`Pages/UpgradePage.cs`, sent by `MainWindow.SendUpgrade` and by `DevSnapshots.Run`; `UpgradesAnswerTests` lists its fields); Swap… → `TrackerService.CampaignOptions`; share preview → `MainWindow.SharePreviewMessage`; share status → `SharingService.Status`.

**Cross-file globals that break easily:**
- core.js's `onHost` assigns globals declared in later files: `lootRows` (loot.js), `sharePreview`/`shareBusy`/`shareStatus` (share.js), `askAnswer` (ask.js), `upg` (upgrade.js), `usagePreview` (settings.js), and reads `usageScroll` (notices.js). webcheck.mjs sends each of those answers (`loot`, `sharePreview`, `shareStatus`, `ask`, `upgrade`, `usagePreview`), so a rename that misses core.js fails the gate. It reads the kinds from the scripts, so a new answer is sent with no list to add it to.
- core.js `show()` calls `drawRace` (home.js), `drawRelevels` (race.js), `drawLootChart`, `syncUpForm`, `requestUpgrade`, `renderAsk`, and writes `askState.q`; core's `[data-go]` click handler (with `data-ask-q`) writes `askState` and `askAnswer`.
- report.js sets core's `heldMessages` and calls `releaseHeld`. ask.js sets core's `metric` and `data.settings.goal` (Ask's own pick); settings.js sets `data.settings.farmDifficulties` and core's `farmWaiting`, which fades Home's and Crawls' verdicts until the next data message. Home reads the relevel's kind from `reinc.homeKind`. home.js, notices.js and settings.js change `data.settings.*` at once; the next data message replaces it.
- race.js lends Home `drawGhost`, `relevelStops`, `stopSeg`, `askSegs`, `gapSegs`, `levelTicks`, `raceRows`, `gapLegend`, and `xpOf` (reads the engine's `reinc.xpByRank`, `Planner.XpByRank`)/`xpWords`/`xpTip` to ask, campaign, crawls, home and roster. campaign.js's `campNext` by home.js.
- core.js's `infoTip` is called inside ask, campaign, home, loot, settings and upgrade templates; core.js also swaps index.html's `<span data-info-slot="key">` placeholders at load.
- settings.js's global `seg`/`sw`: upgrade.js `renderUpPlan` has a local `seg`, ask.js uses `seg2`. The Help page's `[data-action]` click handler (the tour button) is in settings.js, not help.js.

## 7. To change X, touch Y

1. **A field in the page data**: `TrackerService.ReincarnationData` (or a property in `PageData.Build`, and then in `PageDataTests`' `Before` too) → read `data.reinc.<camelCase>` in the page's render function → `node tools/webcheck.mjs`. The `--snapshot` preview follows by itself.
2. **A page request and its answer**: page `post("x", {...})` → `case "x":` in `MainWindow.OnMessage` → a `Send…` method like `SendLoot` (`svc.Query`, serialize `new { kind = "x", ... }` with `PageJson.Options`, `PostWebMessageAsJson`) → `onHost(e => { if (e.data?.kind !== "x") return; ... })` in the page's script, never its own webview listener → for a preview shot, build the answer in `DevSnapshots.Run` and assign it.
3. **A setting**: property on `AppSettings` → `case` in `App.ApplySetting` (check the value, `_settings.Save()`, copy into `_options` if the engine uses it) → a `required` property on `PageSettings` (`Pages/PageData.cs`), in the place it should have in the JSON → filled in `App.SettingsForPage` (the build fails until it is) → its name in `PageDataTests`' `SettingsOnMain` → a `sw(key, …)` or `seg(key, …)` row in settings.js `renderSettings` (its click handler posts `setting`). The `--snapshot` preview follows by itself.
4. **A log line format**: record in `Parsing/LogEvents.cs` → a `[GeneratedRegex]` under LineParser's `patterns (source-generated)` banner and a branch in `ParseLine` (or `ParseYou` for "You …" lines) → `case` in `Tracker.Apply` → `ParserTests`, `TrackerTests` → `docs/log-formats.md`. Fight-meter-only lines: `Combat/CombatParser.cs`. Old logs need re-reading: raise `EngineState.CurrentVersion`, note `reread: true`.
5. **What sharing sends**: records in `Sharing/SharePayload.cs` and `ShareBuilder.Build` (raise `ShareBuilder.Schema` for a new shape) → `ShareUnits.From` → `server/src/sharing.ts` (+ `server/migrations/` for a stored column) → `CommunityJob`/`CommunityBuilder` if the shared numbers use it (`job: true`) → `site/privacy.html` → `ShareTests`. The Settings preview (`MainWindow.SharePreviewMessage`) follows by itself.
6. **A shot in `--snapshot`**: `DevSnapshots.Run`, inside `CaptureWeb(outDir, "main", …)`: `await core.ExecuteScriptAsync("<set globals>; show('x'); render<Page>();"); await shot("name");` → `main-<name>.png`. A window answer it needs: build it in C# and inline it in the `html.Replace("</body>", …)` script, as `askDemo`, `upgradeDemo`, `campDemo` are.
7. **A column in the store**: a new `Visit` property needs none (the `visits.json` column holds the whole visit). `kills`/`loot`/`levels`: the `CREATE TABLE IF NOT EXISTS` in the `PathfinderStore` constructor never changes an existing database and nothing runs `ALTER TABLE`, so add that there; then the positional `INSERT … VALUES` in `Commit`, the record in `Tracking/Records.cs`, the readers (`KillsSince`, `AllLoot`, …). A `CurrentVersion` raise refills rows (`ImportHistoryAsync` → `_store.Reset` deletes rows only).
8. **A page or tab**: `section.page#page-<name>` and a rail `data-page` button (or a `GROUPS` entry) in index.html → core.js `PAGES`, `PAGE_NAMES`, hooks in `render()`/`show()` → a script tag before boot.js → `MainWindow.PageNames` and the inline list in `OnMessage`'s `"seen"` case → the page list in `DevSnapshots.Run` → the `page.<page>` row in `docs/usage.md`.
9. **An Ask question or answer field**: `AskQuery` (`Analysis/Ask.cs`; the page posts `askState` as is) → `AskPage.Build` and its records in `Pages/AskPage.cs` (property order is JSON order) → ask.js `renderAsk` and the builder for that `a.q` (`askLevel`, `askFarm`, …) → `AskQueryTests`, `AskTests` → the `askDemo` list in `DevSnapshots.Run`.
